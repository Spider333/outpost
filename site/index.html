kit: your own node and client for Farcaster

Three commands take you from nothing to a Snapchain read node you control and a client that reads from it and posts through it. No API keys from anyone.

Quickstart

You need a DigitalOcean or Hetzner account with its command line tool logged in, Node.js 20 or newer, and a test account for Farcaster that already has storage.

git clone https://github.com/Spider333/fc-prize kit
cd kit
# rent a server with a 2 TB disk, billed by the hour
./kit provision
# start a read node; the first sync takes 2 to 6 hours
./kit node
# then open http://127.0.0.1:8381
./kit client

When you are done:

# revoke the app key; no recovery phrase needed
./kit uninstall
# delete the server and stop paying
./kit destroy

Every command is safe to run twice. ./kit provision --dry-run prints the exact provider commands without running them.

Before you paste a recovery phrase

A recovery phrase is the custody key of an account. Whoever has it can transfer the account, add or remove every app key, and change the username. Pasting it into the wrong program is like running rm -rf / as root: there is no undo.

  • Use a test account. Never your main account.
  • Only paste a phrase into software whose code you have read, or whose author you trust. That includes this one.
  • Prefer the wallet button. With it, the phrase never leaves your wallet.
  • Revoke the app key when you are done: ./kit uninstall, or "Revoke this key" in the client.

What kit does with a phrase: it derives the custody address in memory, signs one authorization for an app key that can only cast, react and follow and that expires 30 days after last use, then drops it. It never writes the phrase to disk and never sends it over the network. You can check this in src/core/account.ts and src/cli/main.ts.

1. Rent a server

A node keeps a full copy of the network's data. Today that is a snapshot of about 400 GB compressed, and the node needs about 1.5 TB of free disk while it unpacks it, so kit asks for a 2 TB volume. It also asks for 32 GB of RAM: there are reports of nodes with 16 GB crashing.

./kit provision --provider do
# or: ./kit provision --provider hetzner

Here is what it runs, shown with --dry-run (long lines and your home path shortened):

DigitalOcean: droplet kit-node (s-8vcpu-32gb-amd) in fra1 with a 2 TiB volume.
Billed by the hour while it exists: about $0.53/h (droplet + volume, 2025 list prices; check yours).
+ doctl compute ssh-key import kit-node-key --public-key-file /home/you/.ssh/id_ed25519.pub
+ doctl compute volume create kit-node-data --region fra1 --size 2048GiB --fs-type ext4 --desc kit\ snapchain\ data
+ doctl compute firewall create --name kit-node-fw --tag-names kit-node --inbound-rules protocol:tcp\,ports:22\,... protocol:udp\,ports:3382\,...
+ doctl compute droplet create kit-node --region fra1 --size s-8vcpu-32gb-amd --image ubuntu-24-04-x64 --ssh-keys f8:bd:...:0a --user-data-file /tmp/tmp.zxbLVebFF6 --volumes <volume-id> --tag-name kit-node --wait

The firewall opens two ports: 22 for SSH and 3382/udp for gossip, which is how your node talks to the rest of the network. The node's API ports stay closed. Your client reaches them through an SSH tunnel. This matters: by default, a node with an open API port lets anyone on the internet send messages through it.

Already have a server? Skip this step and run KIT_HOST=<ip> ./kit node. It needs Ubuntu 24.04, root SSH and the disk above.

2. Start a read node

./kit node
setting up the read node on 142.93.168.228
[node-setup] data directory: /mnt/snap (1807 GB free)
[node-setup] starting snapchain 0.14.3 (read node)
 Container snapchain-statsd-1  Running
 Container snapchain-snapchain-1  Running
[node-setup] done. HTTP API on 127.0.0.1:3381 once the snapshot has loaded.

This runs the official farcasterxyz/snapchain Docker image, pinned to version 0.14.3, with the official compose file. kit does not use the official installer script, because it reads from /dev/tty and so fails without a terminal, and because with no operator FID it exits before starting the node (issue #1030).

The first sync downloads the snapshot, unpacks it, then catches up on the blocks since. ./kit status shows where it is:

node: downloading snapshot: Progress: 1312/5689 chunks (23%) (ETA: 2h35m)
PENDING: ./kit status output once synced (catch-up line, then "synced").

Read nodes and validators. Snapchain has two roles, run by the same program. Validators propose and vote on blocks; there is a fixed set of them. A read node, which is what you just started, follows the chain, keeps the full state and answers queries. It never votes. Anyone can run one, and it needs no key or paid service: account and key events from the Optimism chain arrive inside the blocks validators produce.

Read nodes also take writes. When your client sends a message, your node checks it, then passes it to validators over gossip. "Accepted" means accepted for relay, not yet in a block, so kit reads every message back from your node before it says "confirmed".

3. Connect an account

./kit client
PENDING: ./kit client output (tunnel line, URL).

On a phone, run ./kit client --phone instead. It serves the client from your server over HTTPS, using a free <ip>.sslip.io name so you need no domain, and puts a password in front of everything, including the node's API.

PENDING: ./kit client --phone output (needs a provider token to open 443).

Open the address it prints. To post, choose Sign with a wallet if your account's custody address lives in a wallet, or Use a test account's recovery phrase. The command-line version is ./kit cli login.

FID. Your account is a number, the Farcaster ID, registered on the Optimism chain. Usernames point to it; posts are signed for it.

Custody. One Ethereum address owns each FID: the custody address. Your recovery phrase is the private key for that address, at the standard path m/44'/60'/0'/0/0. kit derives the address, asks your node which FID belongs to it, and checks that the address is still that FID's custody before it signs anything. No Optimism RPC is needed for this; your node has the registry events.

Storage. The network only keeps messages for accounts that rent storage. One unit bought after July 2025 holds 100 casts, 200 reactions and 200 follows; when you go over, the oldest are pruned. Storage is bought onchain. kit does not buy it; it stops if the account has none.

App keys. You do not sign every post with the custody key. Instead the custody key authorizes an app key, an Ed25519 key the client holds. Since May 2026 this is a plain message to the network, KEY_ADD, with no Optimism transaction and no gas. Each key has:

  • scopes: the message types it may sign. kit asks for casts, reactions and follows only, so it cannot change your profile or verified addresses;
  • a TTL: it expires after 30 days without use (the maximum is 90);
  • a requesting app: the FID of the app that asked for it, signed by that app's custody key. That is how anyone can tell which app posted a cast.

Two details trip people up. The signature uses its own EIP-712 domain, Farcaster KeyAdd with chain ID 1, not the onchain key gateway's domain, so the older helper functions produce signatures the network rejects. And the deadline is in Farcaster time, seconds since 1 January 2021, not Unix time.

Before any account is involved, you can check the signing code against your own node. This builds every message type kit uses with throwaway keys, asks the node to validate each one, and checks that two tampered messages are rejected. It sends nothing.

This run was against a local Snapchain 0.14.3 container. The node's validator checks signatures and message rules, not account state, so it cannot tell you whether a custody signature matches a real account. The unit tests (npm test) cover that with known test vectors.

4. Read and post

Snapchain has no home timeline endpoint. A following feed is the list of accounts you follow (/v1/linksByFid), the latest casts of each (/v1/castsByFid), merged by time. That is one request per account you follow, which is fine on your own node.

PENDING: ./kit cli feed --fid 37 output with timing.
./kit cli cast "hello from the kit CLI on a devnet"
./kit cli follow 422268
./kit cli like 422267 0x77759e8047fd3f44c3754703f7ac5e28072fae79
./kit cli recast 422267 0x77759e8047fd3f44c3754703f7ac5e28072fae79
cast: 0x77759e8047fd3f44c3754703f7ac5e28072fae79 (confirmed: your node returns it)
follow: 0x6fbfe1236ddad27cfe6acc4dea8cd19456124ca8 (confirmed: your node returns it)
like: 0x63511037a5d405e939a04fff8283cc793a2cb7f5 (confirmed: your node returns it)
recast: 0x393567ce0425717647cf18876507d4b65cc43264 (confirmed: your node returns it)

Each line is a message hash. "Confirmed" means kit read that exact message back from your node.

Messages. Every action is a message: a small protobuf with your FID, a timestamp, the action, a BLAKE3 hash of those bytes and an Ed25519 signature from the app key. A cast, a follow, a like and a recast are four message types. Nodes check the signature and that the key is allowed to sign that type, then store the message. Deleting a cast is another message that removes it.

5. Filter by app

A cast does not say which app posted it. But it is signed by an app key, and every app key records the FID of the app that requested it. kit looks this up on your node for every author (/v1/signersByFid) and labels each cast. In the client, tap an app to show only its casts, again to hide them, again to reset. In the command line:

./kit cli feed --fid 37 --exclude 9152
PENDING: feed output with --include / --exclude and the app mix summary.

What this can and cannot tell you:

  • A key a user signed for themselves carries their own FID as the app. Tools that do this, including kit by default, all look the same: "own key".
  • A service that signs for many apps under one FID shows up as one app.
  • An app key copied into another program cannot be told apart.
  • The requesting app cannot be faked: the network checks the app's custody signature. But one developer can register several FIDs.

6. What a keyless node cannot do

Your node runs without an Ethereum RPC endpoint. That is what makes it keyless, and it costs three things. It rejects, and so you cannot submit through it:

  • .eth usernames and other ENS names,
  • ENS username proofs,
  • address verifications for smart-contract wallets.

Casts, reactions, follows, profile fields, plain usernames, normal wallet verifications and app keys all work. To get the three back, add l1_rpc_url with any Ethereum mainnet RPC to the node's config.

7. Societies: a charter file

Filtering by app is one rule. A society is a set of them, written down and signed: who the members are, which apps' posts count, which channels and keywords, and a link to the society's code of conduct. kit calls this a charter. It is one JSON file.

./kit cli charter verify examples/test-society.charter.json

The signature covers every field. Change one member and the file is rejected:

PENDING: verify output for a tampered copy.

If the charter names an issuer FID, kit also checks on your node that the signer is that account's custody address. Nobody else can sign for the society.

In the client, load a charter in the Society panel. The feed then shows the society's members and channels, through its rules. Join follows its members with your app key. Leave drops the lens. Your keys, follows and posts do not change, because they were never the society's to begin with. Leaving is one tap.

The census counts members, members who posted in the last 7 days, casts per day, and the apps members post from. It reads only your own node, so anyone with a node and the same file gets the same numbers.

./kit cli charter census examples/test-society.charter.json
PENDING: census output, and the hand count it was checked against.

A charter is a lens, not a wall. It changes what you see and whom you follow. It cannot stop anyone posting, and it hides nothing from anyone else.

8. Clean up

./kit uninstall
revoked app key 0x5cbcb91837b9b4160f82bed08680c8884911c6af1b83a3f6047b80847260f4f4 for FID 422267. No recovery phrase was needed.
deleted ~/.config/kit/appkey.json

Casts the key signed stay on the network after it is revoked. (Checked on Snapchain 0.14.3: the cast above is still there after the key is gone.) Delete them first with ./kit cli delete <hash> if you want them gone.

The key signs its own removal (KEY_REMOVE), so no recovery phrase is needed. If you never revoke it, it expires 30 days after its last use.

./kit destroy

This deletes the server, the volume and the firewall after you type the server's name. Your account, follows and casts are not affected; they live on the network.
